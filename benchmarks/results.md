# Измерения 12 ноября 2026

Это сохранённый двухсторонний baseline. Последующий трёхсторонний замер с native
hybrid runtime и учётом mutation: [hybrid-results.md](hybrid-results.md).

В этой реализации native выигрывает по стоимости привязок. При N=1000 DSL тратит
на них **8.53 / 10.96 / 10.58 мс** для изменения одного поля / всех полей /
перестановки, native — **0.56 / 0.72 / 0.73 мс**. Разница около 15× относится
именно к этой фазе, а не ко всему кадру.

Это текущий интерпретируемый DSL против C++ data model. Точные условия, границы
фаз, dirty-гранулярность, различие keyed/positional и охват аллокаторов описаны
в [методике](README.md). Участники не дают одинаковых гарантий сохранения состояния
при перестановке; результат нельзя переносить на любой возможный native-мост.

## Условия

- Intel Core i9-14900HX; Windows 11, build 26200.
- Реально выбранный GL renderer: **Intel RaptorLake-S Mobile Graphics Controller**,
  GL 3.3, driver 32.0.101.6881.
- MSVC 19.38.33130 x64, Release `/O2 /Ob2 /DNDEBUG`; RmlUi 6.4-dev.
- 800×700, DPI 1, без swap/present; каждый кадр заканчивается glFinish и явным GC.
- 4 временных раунда × 120 кадров = **480 временных измерений на каждую фазу
  каждого сценария/движка**; перед каждым раундом 30 кадров прогрева.
  Ещё 120 кадров в отдельном раунде памяти. Порядок DSL/native чередуется.
- Нижняя граница инструмента (median пустого интервала): 0.1 мкс; не вычитается.
- Частота CPU не фиксировалась, прочие приложения не выключались. Во время
  измерений агент не запускал сборку, CTest или второй benchmark параллельно.

[Metadata, версии и SHA256 исходников](results/2026-11-12/environment.json).
Рабочая копия содержала незакоммиченные изменения, поэтому один git HEAD не

## Время, N=1000

Медианы в **миллисекундах на кадр**. Render — CPU-время вызова; wait — отдельное
остаточное ожидание GPU, не GPU timestamp. GC относится ко всему script Context.
Сумма медиан фаз не является медианой полного кадра.

| Все поля | DSL | 10.957 | 2.992 | 5.747 | 1.190 | 1.820 |
| Все поля | native | 0.716 | 3.015 | 5.603 | 1.167 | 0.194 |
| Перестановка | DSL | 10.579 | 4.462 | 3.966 | 1.178 | 1.832 |

## Выделения, N=1000

В каждой ячейке **среднее число запросов / KiB на кадр**, отдельный раунд памяти.
C++ — main-thread new/new[]; daScript — логические heap/stringHeap allocations.
Эти уровни могут пересекаться, поэтому **их нельзя складывать**. Это не RSS/VRAM
и не все системные выделения. Новая память не обязательно остаётся живой после GC.

| Путь | Сценарий | C++ Bindings | C++ Update | C++ Render | daScript Bindings |
|---|---|---:|---:|---:|---:|
| DSL | Простой | 2 / 0.1 | 0 / 0 | 0 / 0 | 2025 / 36.4 |
| native | Простой | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| DSL | Одно поле | 4010 / 375.6 | 7025 / 306.8 | 3000 / 875.0 | 6054 / 478.1 |
| native | Одно поле | 19 / 25.1 | 7025 / 306.8 | 3000 / 875.0 | 0 / 0 |
| DSL | Все поля | 6008.1 / 578.6 | 7025 / 306.8 | 3035 / 875.5 | 8052 / 797.0 |
| native | Все поля | 19 / 25.1 | 7025 / 306.8 | 3035 / 875.5 | 0 / 0 |
| DSL | Перестановка | 4008.2 / 375.5 | 11021 / 650.3 | 3022 / 1003.4 | 6052 / 477.8 |
| native | Перестановка | 19 / 25.1 | 7025 / 306.8 | 3035 / 875.5 | 0 / 0 |

В Update, Render и GPU wait логические daScript-выделения равны нулю. У GPU wait
также нет посчитанных C++ allocations. GC освобождает временные daScript-объекты
и имеет свои C++ allocations; точные значения и `das_live_delta` есть в CSV.

## Что следует из измерений

1. **Точечное вычисление выражений ещё не означает точечную стоимость кадра.**
   Smoke подтверждает 0/1/N/0 обновлений текстовых привязок. Но снимки зависимостей,
   обход структуры и bookkeeping остаются: даже idle выделяет 2025 логических
   объектов daScript при N=1000. Это приоритетное место для оптимизации runtime.
2. При изменении одного текста Update всё равно занимает около 3 мс у обоих путей:
   данный flow-layout затрагивает список. Только ускорения bindings недостаточно,
   чтобы сделать такой кадр почти бесплатным.
3. Keyed DSL снижает Render при rotate за счёт сохранения элементов с прежним
   текстом, но делает более дорогие bindings и Update. У native дешевле подготовка,
   однако `data-for` не сохраняет соответствие записи и DOM-элемента по ключу.
4. Следующее направление для DSL — адресная dirty-инвалидация и стабильные записи
   зависимостей/ключей, сокращение временных строк и снимков коллекций. Для длинных
   списков также стоит отдельно измерить уже имеющуюся виртуализацию. Это вывод
   о приоритетах по профилю расходов, не измеренный результат будущей оптимизации.
